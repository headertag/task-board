# Controlled Worker authentication

This branch replaces proxy identity headers with WorkOS AuthKit + Connect. The current repository uses the existing Vinext/Cloudflare Worker adapter; its build and D1/R2 interfaces are retained. No framework migration is required. An existing private Site stays authoritative until the separate synthetic gate and authorized cutover in [oauth-cutover.md](oauth-cutover.md) pass.

## Approved configuration, then deployment

Do the implementation and local synthetic checks first. Account login, OAuth clients/grants, provider credentials, allowlist changes, DNS, resource creation, spend and production cutover need their owner's explicit approval. None of the example files create those resources. Start with the provided `authkit.app` domain; do not purchase a custom authentication domain or upgrade a Cloudflare plan implicitly. Confirm current WorkOS Connect quotas and Cloudflare CPU/storage costs before any paid commitment.

1. Have the owner select the existing Cloudflare account and WorkOS staging environment, approve the narrow deployment scope, and complete provider credential entry privately.
2. In the approved staging environment enable Google and GitHub social sign-in. Disable other login methods if sign-in must occur through those providers. WorkOS bundled social credentials are for staging; production social credentials must belong to the owner. The upstream Google/GitHub callbacks are supplied by WorkOS and differ from browser and external MCP client callbacks.
3. Register the board's exact HTTPS `/mcp` URL as a Connect resource indicator. Tokens must have that exact audience. Send the exact `resource` in both authorization and token requests. WorkOS's configured default resource applies to DCR/CIMD applications, so do not assume it repairs a missing parameter for an explicitly preregistered client. Never accept the environment client ID as a fallback audience in the board.
4. Approve the external MCP client's exact callback privately and choose CIMD, DCR or explicit Public PKCE preregistration supported by that client. Enable CIMD/DCR only after approval; the metadata proxy advertises actual upstream capabilities. Prefer a third-party client that requires owner consent. Verify a fresh grant displays consent. Client labels and public registration confer no board permissions.
5. Register a separate Public PKCE browser application for the board with the exact `${TASK_BOARD_ORIGIN}/auth/callback` URI. Confidential applications are WorkOS's default and cannot use this no-client-secret flow. Browser authorization uses `openid profile email`, S256, state and nonce. External-agent redirect URIs are not committed to this repository.
6. Obtain the authoritative WorkOS user ID, verified email and Google/GitHub `idp_id` after owner sign-in. Review a private `TASK_BOARD_AUTH_POLICY` mapping those identities to the existing storage owner. The fictional [policy example](../auth-policy.example.json) is not a real grant. GitHub requires its immutable provider ID, never a username. Google email matches require WorkOS `email_verified=true` and a linked Google identity; pin the provider ID and WorkOS user ID as well for migration. Multiple selectors on one rule are conjunctive; identities on one owner are alternatives. Ambiguous owner matches fail closed.
7. Build with `npm ci`, `npm run setup`, `npm test`, `npm run typecheck`, and `npm run build`. Copy [wrangler.example.jsonc](../wrangler.example.jsonc) to ignored `wrangler.private.jsonc`, set the approved staging binding IDs, and apply schema-only `drizzle/*.sql` in order to the authorized destination. Never reuse the all-zero database placeholder remotely.
8. Enter `WORKOS_API_KEY`, `TASK_BOARD_SESSION_SECRET` and `TASK_BOARD_AUTH_POLICY` through the approved private secret handoff. The API key is used only to retrieve users and linked identities from WorkOS. Use the narrowest provider-supported permissions for those endpoints. Generate the session secret as 32 cryptographically random bytes encoded in unpadded base64url (43 characters); keep it stable across replicas and rotate deliberately. Store the policy as valid JSON with no leading or trailing whitespace. Configure the issuer, audience, browser client ID and HTTPS origin from [.dev.vars.example](../.dev.vars.example). Do not store real values in Git or chat.
9. Use the already-authorized Cloudflare deployment identity to publish this build through the private configuration. Keep `TASK_BOARD_READ_ONLY=true` except while explicitly authorized to create synthetic fixtures or test mutations. Images must remain in a private R2 bucket and pass through the authenticated application route. Complete the hosted acceptance and recovery gates before an authorized production switch.

## Production preparation

WorkOS staging environments and bundled Google/GitHub credentials are intended for testing. Use a production WorkOS environment, owner-controlled social credentials and its actual provider callbacks for real customer-facing traffic. WorkOS requires billing information to unlock production even within AuthKit's free tier; review current pricing and quotas with the owner before activation. An approval to deploy application code does not create a billing commitment or authorize new social-provider credentials. See [environment isolation and production setup](https://workos.com/docs/authkit/environments), [Google configuration](https://workos.com/docs/integrations/google-oauth), [GitHub configuration](https://workos.com/docs/integrations/github-oauth) and [current pricing](https://workos.com/pricing).

Record the production issuer, API-key scope, exact resource, Public PKCE browser client, approved external client/callback, private session secret and authoritative identity evidence in a private deployment manifest. Verify every identifier in that environment; do not copy staging user/client IDs or assume a staging user mapping remains valid. Keep the legacy storage owner explicitly bound to the verified production identity. Changing issuer/origin/client configuration invalidates existing sessions and requires fresh sign-in and external-agent consent. Re-run the hosted synthetic gate against the production configuration before importing real records. A custom DNS/authentication domain is optional and requires a separate authorized domain configuration if chosen.

## Cloudflare CLI scopes and prerequisites

The locked Wrangler 4.92.0 supports this explicit OAuth scope subset for account/user identification, Worker deployment and secrets, and D1 creation:

```sh
npx wrangler login --scopes account:read user:read workers_scripts:write d1:write
```

Wrangler adds `offline_access` automatically. Before running login, obtain the owner's explicit approval for these exact scopes, persistent access, target account and operations. These scopes are not restricted to one staging Worker and can grant account-wide capabilities wherever the signed-in identity has access; a configured account ID is not a permission boundary. Omitting `--scopes` requests Wrangler's broad defaults, which must not be inferred as approved. See [Wrangler login](https://developers.cloudflare.com/workers/wrangler/commands/general/#login), [Worker script permissions](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/methods/update/), [Worker secret permissions](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/secrets/methods/update/) and [D1 creation permissions](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/create/). Current documentation may describe login flags absent from the locked version.

Wrangler 4.92.0 exposes no R2 OAuth scope, and the OAuth mapping needed for bucket creation remains unverified. Do not infer that a broader default scope supplies it. Separately authorize the owner to create the private staging bucket in the Dashboard; the [R2 creation API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/methods/create/) requires Workers R2 Storage Write. Worker deployment can bind existing D1/R2 resources without separate storage permissions under [granular Worker authorization](https://developers.cloudflare.com/workers/authorization/workers/#bindings).

Use native Worker assets and `routes: []` with the approved Workers subdomain to avoid legacy KV asset storage, route publication and custom-domain permissions. No plan upgrade, purchase or unrelated resource permission is implied by staging setup.

## Request trust and permissions

Every MCP method, board API action and image request verifies the caller. The Worker strips old `oai-authenticated-user-*` headers and the application never consumes them. Connect tokens use the configured issuer's fixed `/oauth2/jwks`, RS256, exact resource audience, required expiry/issued-at and user subject, client ID and consent ID. Machine credentials and delegated actor tokens are rejected. Invalid Authorization never falls back to browser cookies.

Browser login exchanges the code with its S256 verifier and verifies the ID token's signature, issuer, browser audience, expiry, nonce and authorized-party claim. State is single-use through an atomic D1 delete. AES-GCM seals an expiring session with origin/client/purpose binding in a Secure HttpOnly SameSite=Lax `__Host-` cookie. Each request re-fetches the WorkOS user and provider identities and re-evaluates the private allowlist. Provider identity calls, browser token exchange and metadata discovery use Workers-supported manual redirect handling and reject redirects before credentials can follow them. Sessions expire within an hour; the initial implementation asks the user to sign in again rather than persisting refresh tokens. Browser POST mutations require the exact Origin and reject cross-site requests. Sign-out is `POST /auth/signout` with the same checks.

External clients, including newly registered ones, default to read-only. Optional `owners[].agentAccess` accepts `"read"` or `"write"`; omission means read-only. An owner-approved `"write"` value delegates task mutations to **all otherwise-unlisted clients** presenting a valid signed user token for that owner and the exact single MCP resource, with `client_id` and consent `sid`. This includes DCR/CIMD clients and existing valid grants. Every identity rule on a write-delegating owner must pin both its immutable provider ID and WorkOS user ID. Verified email/provider/user selectors remain conjunctive, and an unmapped identity still receives 403. Standard OIDC scopes, client names and token permission labels are not the write grant; the private owner policy is.

Explicit client entries take precedence over owner delegation. `access: "read"` denies writes even for a write-delegating owner. `access: "write"` continues to require its configured custom non-OIDC `writeScope` in the signed token; owner delegation cannot substitute for that scope. WorkOS DCR/CIMD clients cannot be assigned per-client custom scopes, so owner delegation provides an explicit server-side permission without inventing vendor scopes. Removing the delegation or adding a client read restriction takes effect on subsequent requests, including requests using an already issued token. Browser owners and agents may mutate only when `TASK_BOARD_READ_ONLY=false`; missing flags freeze writes and malformed values fail closed. Keep the lock active throughout migration regardless of delegated rights.

The resource server checks current identity/allowlist on every request, but does not promise immediate cancellation of an already issued JWT after OAuth consent revocation. Consent IDs prove issuance under a signed user grant; access JWTs remain expiry-bounded. WorkOS introspection requires OAuth application credentials, so immediate consent revocation needs a separately verified, approved vendor-supported resource-server setup. Do not add or reuse unrelated client secrets to work around that prerequisite.

## Discovery and verification

`GET /.well-known/oauth-protected-resource` and its `/mcp` variant publish the exact MCP resource, issuer and minimal OIDC scopes. `401` responses challenge with that metadata URL. Legacy `/.well-known/oauth-authorization-server` and `/mcp` paths relay validated provider metadata, including real registration capabilities and S256 support. `/.well-known/openid-configuration` relays validated OIDC discovery. These paths are handled in the retained Worker entry because this adapter omits hidden App Router directories.

`npm test` includes real synthetic RSA-signed tokens, authoritative provider responses simulated without network, browser code/state/nonce/PKCE checks, mapped owner access and route negatives. This proves the code boundary; it is not evidence that a live provider account or a particular external client has been configured successfully. Run the owner's actual external-client OAuth flow against an authorized synthetic staging board and complete the full [cutover gate](oauth-cutover.md) before migrating real data.

Primary references: [WorkOS MCP](https://workos.com/docs/authkit/mcp), [Public PKCE applications](https://workos.com/docs/authkit/connect/oauth), [Connect scopes and claims](https://workos.com/docs/authkit/connect/token-claims), [WorkOS OAuth authorize](https://workos.com/docs/reference/workos-connect/authorize), [token endpoint](https://workos.com/docs/reference/workos-connect/token), [identity API](https://workos.com/docs/reference/authkit/identity), [metadata](https://workos.com/docs/reference/workos-connect/metadata), [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).

The optional built-Worker persistence suites require `TEST_CREDENTIALS_PATH` pointing to a private JSON file with `{synthetic:true,ownerId,writeToken,readToken,otherOwnerId,otherWriteToken}`. Use two explicitly mapped, empty synthetic owners per creation suite, fresh fixture credentials for the separate task and image suites, and newly supplied read credentials for restart verification. Probes store record IDs and owner IDs, never tokens. These suites are not a substitute for live external-client OAuth verification.

Local runtime caveat: repeated anonymous `POST /api/board` (body `{}`), `GET /api/images?id=<synthetic-id>`, POST, GET requests on one connection can stall in loopback Wrangler. The same sequence reproduces on untouched source main with the locked Wrangler/Vinext versions and fresh local bindings. Unit/route tests and successful individual HTTP responses do not prove this adapter/runtime path is reliable. Keep hosted synthetic OAuth/image/concurrency verification as a release gate; do not probe production or change frameworks as an implicit workaround.
