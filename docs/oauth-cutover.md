# OAuth hosting cutover and rollback

The existing private board and its records remain authoritative until a verified, owner-approved cutover. Implementation, a draft pull request, an OAuth provider recommendation and a passing unit test do not authorize moving real task data or switching production. Keep deployment identifiers, social credentials, allowed identities, client callbacks, migration manifests and task data in private configuration outside this public repository.

## Private migration record

Before any destination data writes, record and have the owner approve an explicit mapping from the legacy storage owner to the new verified immutable principal. Capture the issuer and subject, stable upstream provider identity ID when relevant, verified email evidence, and the canonical storage owner key chosen for that principal. Use stable provider IDs rather than mutable GitHub usernames. Do not infer ownership from an email match, an agent label, a caller-supplied header, or invitation-only signup. A verified email allowlist is an admission rule; it does not merge multiple owners' records.

The mapping must identify exactly one existing owner and one authorized destination owner. If the application's configured owner binding preserves the legacy storage key, retain that key explicitly. If an authorized exact restore uses a new storage owner key, re-key only the storage ownership and private image-object namespace; preserve every task, comment, attachment and snapshot ID, record payload, timestamp, revision, request key and history fingerprint. Multiple approved sign-in methods for the same human require explicit owner bindings; never auto-link records because display names or email strings look similar. Preserve denied/revoked identity behavior after mapping.

Keep a private migration record containing the approved mapping, source and destination targets, source backup ID and whole-file digest, verified manifest counts, every image digest, application/schema revision, credential/allowlist configuration revision, validation results and cutover boundary. Secrets and task text do not belong in operational logs. Repository examples must use placeholders only.

## Synthetic acceptance gate

Use a separately approved, isolated destination with fictional data first. No real task export, account migration, production DNS change or old-board write-policy change is part of this gate. Approval for new accounts, OAuth/social clients, grants, keys, allowlist configuration, deployment resources or spending must identify the action, target, scope and expected cost before execution.

1. Authenticate the synthetic owner through the selected browser identity provider. Verify stable provider identity and verified email evidence, then apply the explicit owner binding and current allowlist on browser, API, MCP and image requests. Create a known fictional fixture containing task revisions, Trash, comments including a removed comment, an attached PNG, a retained unattached draft upload and a recovery snapshot. Record expected IDs, revisions and image hashes in private gate evidence.
2. Verify protected-resource and authorization-server discovery from the destination origin. With the owner present and consenting to read-only task access, complete the actual external agent's browser OAuth flow using its approved callback/client registration mode and PKCE. Keep the real callback and any client identifiers in private configuration. Confirm that the agent reads the exact expected synthetic task/comment IDs and the same latest revisions as the browser/API. Identity authorization and read/write permissions must be enforced in application code; do not assume custom task scopes are issued to dynamically registered clients merely because standard OIDC scopes were returned.
3. Exercise denied access: anonymous browser/API/MCP/image requests, forged identity headers, an unapproved Google identity, an unapproved GitHub identity, a different allowed owner's records/images/cursors, invalid token signatures, wrong issuer or audience, expiry, wrong PKCE verifier, wrong OAuth state, redirect mismatch and authorization-code replay. Revoking an identity must affect subsequent requests. Confirm that the read-only agent cannot create/edit/archive/import or otherwise mutate data. Public protocol metadata must reveal no private records.
4. Exercise writes using separately authorized synthetic browser/API clients. Two edits with the same expected revision must produce one winner and a conflict; re-read and reconcile the loser. Identical mutation retries must return the same result with the same request key, and changed arguments under that key must be rejected. Test independent comment revisions, archive/restore, comments/images surviving task Trash and private image retrieval with no anonymous bypass. Agent names and labels must never confer rights.
5. Download every complete v2 backup page and validate chain, counts, relationships and all image bytes. Rehearse offline exact recovery under the explicitly mapped fictional destination owner in an empty private directory. Verify all record IDs, histories, revisions, timestamps and request keys, plus byte-identical images including retained drafts. Repeat recovery to prove idempotency. A portable copy import is not an exact recovery because it assigns new IDs.
6. Rehearse rollback both before destination writes and after a fictional post-cutover task/comment/image change. Demonstrate that post-cutover writes survive reconciliation with IDs and revision chains intact. Record evidence and unresolved limitations. Pass this gate only after the actual agent flow and these destination checks have succeeded; offline fixtures cannot prove external client interoperability.

## Approved real-data cutover

After the synthetic gate passes, request authorization for the exact real-data source, destination, immutable-owner mapping and planned read-only window. New production resources, provider settings, clients, credentials, grants, DNS/security changes or costs require their own explicitly scoped approval. Review the destination's access policy and permitted data handling before transfer. A staging provider connection or a bundled social credential does not establish production ownership.

Prepare the rollback application/configuration revision and private source D1/R2 targets before switching traffic. Verify that the original hosting service can enforce the planned read-only window across every mutation route; if it cannot, stop cutover and resolve that prerequisite. Keep the old board reachable under its existing access controls. Disable writes for the cutover boundary, wait for already accepted writes to finish, and prevent writes through stale browser tabs or agent connections. Only one board may accept writes after the boundary.

Capture and keep an untouched, fully validated v2 source backup during that read-only window. Also retain owner-authorized platform/database/object snapshots when available; the portable backup remains independently recoverable. Record manifest counts, source high-water boundary, backup digest and image hashes. Rehearse exact local restoration of this final capture before moving it to the approved destination. The offline `recover-backup.mjs` command creates an isolated SQLite database and image directory; it does not write live D1/R2 resources. A reviewed, separately authorized deployment migration must target only the named destination and preserve the approved owner mapping and every record ID. Do not use `import_tasks` for this operation.

Verify the destination against the final source capture using browser, API and the consented external agent: exact record IDs, current revisions, history/comment/snapshot counts, recoverable removals and every normalized PNG byte/hash. Check the denial matrix again against the real destination without exposing task text in evidence. Verify a complete destination backup and its isolated exact restore. Confirm the scheduled local destination, owner-only permissions, approved credential-renewal method and failure reporting; scheduling remains an explicit operational action.

The parent/owner must approve the verified cutover result before enabling destination writes or switching production. Record the moment and owner mapping. Keep the original board read-only and keep the final source snapshot untouched for the agreed rollback period. Monitor only through already authorized credentials and avoid accepting writes on both systems.

## Rollback without losing post-cutover work

If no destination writes were accepted, restore the previous routing/configuration only after confirming that boundary; verify the untouched source and access checks, then reopen source writes with approval. Preserve the failed destination and evidence for diagnosis.

If destination writes were accepted, make both boards read-only and drain in-flight mutations before rollback. Capture a complete verified destination v2 backup and retain the original pre-cutover snapshot. Identify post-cutover events by the recorded cutover boundary, stable record IDs and request keys; timestamps alone are insufficient. Compare task and comment revision chains, newly created records, archive/restore state, snapshots and all new/retained image bytes. Resolve conflicting changes explicitly with the owner. Do not replace the source with an old snapshot or perform a portable copy import, since either can lose updates or change IDs.

Reconcile the verified post-cutover changes into an isolated exact recovery or a separately approved owner-scoped migration, preserving event order, request-key idempotency, revisions and image relationships. The existing offline recovery tool validates a single capture and intentionally does not merge two live databases; a conflicting merge therefore needs a reviewed migration procedure. Rehearse and verify the reconciled result before enabling source writes or switching traffic back. If reconciliation cannot be proved safe, keep both boards read-only and preserve both captures until the owner decides how to resolve the conflict. Never silently discard destination writes to make rollback appear complete.
