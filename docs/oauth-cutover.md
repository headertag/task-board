# OAuth hosting cutover and rollback

The existing private board and its records remain authoritative until a verified cutover within the owner's authorized production scope. A production request authorizes preparation; passing code tests or publishing a staging Worker does not establish that the live authentication, client, image and recovery gates have passed. Keep deployment identifiers, social credentials, allowed identities, client callbacks, migration manifests and task data in private configuration outside this public repository.

## Production readiness

The repository implements protected browser/API/MCP/image access, ordinary complete v2 backups, separate full-state v3 migration captures and isolated offline recovery. V3 preserves original completed-upload retries under the unchanged legacy storage owner and refuses pending reservations. The reviewed owner-scoped production D1/R2 importer is described in [production-deployment.md](production-deployment.md); it is separate from copy import and offline recovery. No two-database conflict merger or automatic backup credential renewal is supplied. `import_tasks` is a copy operation with new IDs and cannot perform an exact migration.

Pass the owner's actual external-agent OAuth flow using trusted HTTPS, the approved callback/registration mode and S256, then verify exact fictional record IDs and read-only permissions. A supplied token or an offline route test does not prove that flow. Certificate-chain failures or inability to complete browser sign-in leave this gate pending; do not disable TLS verification to make it appear successful. Upload and read back every hosted fixture PNG, including Trash, removed-comment and retained draft images. Missing R2 objects or an incomplete image-bearing backup block release even when task reads work.

Production needs its own approved WorkOS environment, issuer, resource audience, browser/external client settings and owner-controlled social-provider credentials. Reauthenticate the owner there and verify immutable provider IDs, WorkOS user ID and verified email before installing the production allowlist. Staging/demo identities, bundled staging social credentials, existing staging grants and copied policy entries are not a verified production identity mapping. Resolve any new resource, credential, grant or cost approval within the exact named production scope; a staging setting must not be silently promoted.

## Private migration record

Before any destination data writes, record and have the owner approve an explicit mapping from the legacy storage owner to the new verified immutable principal. Capture the issuer and subject, stable upstream provider identity ID when relevant, verified email evidence, and the canonical storage owner key chosen for that principal. Use stable provider IDs rather than mutable GitHub usernames. Do not infer ownership from an email match, an agent label, a caller-supplied header, or invitation-only signup. A verified email allowlist is an admission rule; it does not merge multiple owners' records.

The mapping must identify exactly one existing owner and one authorized destination owner. If the application's configured owner binding preserves the legacy storage key, retain that key explicitly. The supplied v3 migration/recovery path requires retaining the legacy storage owner key and refuses re-keying, because upload IDs are owner-derived. Bind the verified new authentication principal explicitly to that existing key. Preserve every task, comment, attachment and snapshot ID, record payload, timestamp, revision, task/comment request key and history fingerprint. A different storage-key migration requires a separately reviewed solution and is not implemented by v3. Multiple approved sign-in methods for the same human require explicit owner bindings; never auto-link records because display names or email strings look similar. Preserve denied/revoked identity behavior after mapping.

Keep a private migration record containing the approved mapping, source and destination targets, source backup ID and whole-file digest, verified manifest counts, every image digest, application/schema revision, credential/allowlist configuration revision, validation results and cutover boundary. Secrets and task text do not belong in operational logs. Repository examples must use placeholders only.

## Attachment upload retry continuity

The current complete v2 backup preserves record content, IDs, task/comment histories and mutation request keys/fingerprints, snapshots, completed attachment metadata and all their normalized PNG bytes, including retained drafts. It captures only upload rows marked `ready=1`; interrupted or pending reservations require separate review after writes are drained. It does not export attachments' original database `request_key` or upload `fingerprint`. Offline recovery writes `recovered:<attachment-id>` and the image SHA-256 instead. A successful capture and repeated exact recovery therefore prove content/history recovery, not continuity of original upload retries or a raw database clone.

Upload IDs are derived from the storage owner and upload request key. Retrying a pre-migration upload under the unchanged storage owner can encounter the restored row's different fingerprint and return `idempotency_conflict`; remapping that owner changes the derived ID and can create another attachment. Preserving old attachment IDs and bytes alone does not prevent either result.

Preserve import snapshot IDs and payloads, including `source:<import-request-key>` and `before:<import-request-key>`, because they guard import retries and identify the original input/boundary. An attachment-bearing import retry depends on upload retry continuity as well as preserved task/comment mutation keys.

Use the separate `export_migration_page` v3 operation for the supplied migration path. Its private manifest contains the authoritative `storageOwner`, `ownerTag=SHA-256(storageOwner)`, completed-attachment retry keys/fingerprints and a retry count; its HMAC cursors bind the version and owner. The validator verifies the storage-owner/hash relationship, every page and retry fingerprint, and offline recovery also checks original owner-derived upload IDs before writing. It restores original retry fields and refuses a different storage owner. Synthetic tests prove original-key replay, changed-input rejection, pending-reservation refusal, cursor isolation and repeated exact restore. Ordinary v2 backup remains unchanged and weaker.

Before real cutover, freeze the source and drain writes/uploads, resolve all pending reservations, capture all v3 pages through the existing authorized source identity, and verify upload retry behavior again after destination readback. Do not substitute a v2 capture or silently promote a content-only v2 recovery. A reviewed raw source migration is an alternative; changing the storage owner still requires a separate solution for owner-derived upload IDs.

## Synthetic acceptance gate

Use a separately approved, isolated destination with fictional data first. No real task export, account migration, production DNS change or old-board write-policy change is part of this gate. Approval for new accounts, OAuth/social clients, grants, keys, allowlist configuration, deployment resources or spending must identify the action, target, scope and expected cost before execution.

1. Authenticate the synthetic owner through the selected browser identity provider. Verify stable provider identity and verified email evidence, then apply the explicit owner binding and current allowlist on browser, API, MCP and image requests. Create a known fictional fixture containing task revisions, Trash, comments including a removed comment, an attached PNG, a retained unattached draft upload and a recovery snapshot. Record expected IDs, revisions and image hashes in private gate evidence.
2. Verify protected-resource and authorization-server discovery from the destination origin. With the owner present and consenting to read-only task access, complete the actual external agent's browser OAuth flow using its approved callback/client registration mode and PKCE. Keep the real callback and any client identifiers in private configuration. Confirm that the agent reads the exact expected synthetic task/comment IDs and the same latest revisions as the browser/API. Identity authorization and read/write permissions must be enforced in application code; do not assume custom task scopes are issued to dynamically registered clients merely because standard OIDC scopes were returned.
3. Exercise denied access: anonymous browser/API/MCP/image requests, forged identity headers, an unapproved Google identity, an unapproved GitHub identity, a different allowed owner's records/images/cursors, invalid token signatures, wrong issuer or audience, expiry, wrong PKCE verifier, wrong OAuth state, redirect mismatch and authorization-code replay. Revoking an identity must affect subsequent requests. Confirm that the read-only agent cannot create/edit/archive/import or otherwise mutate data. Public protocol metadata must reveal no private records.
4. Exercise writes using separately authorized synthetic browser/API clients. Two edits with the same expected revision must produce one winner and a conflict; re-read and reconcile the loser. Identical mutation retries must return the same result with the same request key, and changed arguments under that key must be rejected. Test independent comment revisions, archive/restore, comments/images surviving task Trash and private image retrieval with no anonymous bypass. Agent names and labels must never confer rights.
5. Download every v3 migration capture page and validate chain, owner tag, retry metadata, counts, relationships and all image bytes. Also verify that the ordinary v2 backup remains available. Rehearse offline exact recovery under the explicitly mapped fictional destination owner in an empty private directory. Verify all record IDs, histories, revisions, timestamps and task/comment mutation request keys, plus byte-identical images including retained drafts. Repeat recovery to prove idempotency. Replay original attachment upload keys under the unchanged storage owner and verify changed-input rejection. The synthetic rehearsal establishes the code behavior; repeat the comparison and hosted retry readback for real destination data. A portable copy import is not an exact recovery because it assigns new IDs.
6. Rehearse rollback both before destination writes and after a fictional post-cutover task/comment/image change. Demonstrate that post-cutover writes survive reconciliation with IDs and revision chains intact. Record evidence and unresolved limitations. Pass this gate only after the actual agent flow and these destination checks have succeeded; offline fixtures cannot prove external client interoperability.

## Approved real-data cutover

After the live synthetic gate passes, confirm the exact authorized real-data source, destination, immutable-owner mapping and read-only window. Honor already recorded owner authorization; resolve any missing target, data-handling, resource, credential, grant, DNS/security or cost scope before the dependent action. Keep synthetic test data separate from the destination owner receiving real records.

1. Prepare the previous application/configuration revision and private source database/object targets for rollback. Deploy and verify the auth-preserving source write lock on every board API, MCP mutation and image-upload route while export reads remain available. The destination's `TASK_BOARD_READ_ONLY` setting does not freeze the original Site. Merely closing tabs or hiding controls cannot block stale callers. Freeze both boards, drain accepted writes/uploads and block stale tabs or agent mutations. Review any unfinished upload reservations. If source write enforcement or the upload retry-state release gate cannot be proved, stop before transfer.
2. Capture the source through an already authorized owner session, separate migration-download path or authenticated `export_migration_page` operation. The ordinary complete-backup UI still produces v2; select v3 explicitly. The local capture script accepts an authorized bearer for `/api/board`; it does not sign into a legacy hosting service, follow redirects or manufacture proxy identity headers. Follow every cursor, validate the complete chain, counts, revisions, relationships and image hashes, and retain the untouched capture with its whole-file digest. Require version 3 and validate the unchanged storage owner plus every completed-upload retry key/fingerprint. If the legacy Site cannot expose authoritative v3 metadata, keep migration blocked until its auth-preserving migration preparation is deployed. Record the source boundary, storage owner, schema/application revision and retry-state inventory privately.
3. Copy the capture into an isolated private recovery directory, restore under the explicit owner mapping and repeat the same recovery to verify idempotency. Check current and archived tasks, active/removed comments, all histories and snapshots, completed attachment IDs/bytes, and retained unattached drafts. Restore the v3 original upload keys/fingerprints under the unchanged storage owner and replay retries. A copy import and a content-only v2 recovery do not satisfy the full-state migration requirement.
4. Prepare and review an owner-scoped SQL/object migration package for the exact empty destination owner. Preserve record IDs, task/comment request keys and fingerprints, snapshots, attachment retry fields and approved ownership; inventory every object key, size and SHA-256. Apply compatible schema migrations, upload verified objects into the private namespace, and apply the reviewed data writes while application writes remain disabled. Do not overwrite unrelated owners or treat the local SQLite database as a ready-made remote D1 restore. Use the reviewed v3 production importer documented in [production-deployment.md](production-deployment.md), including its explicit target configuration, empty-target checks and object verification; never substitute `import_tasks`.
5. Read back the named destination through browser, API and the freshly consented read-only external agent. Compare exact current/Trash task IDs and revisions, comment removals/history, snapshot payloads and every completed PNG byte/hash against the source capture. Verify authoritative upload retry fields and original-key retry behavior. Run the denial matrix with production settings, download a complete v3 destination migration capture and rehearse its isolated recovery. Verify ordinary v2 backups as well. Compare canonical records, timestamps, ordered histories, mutation keys/fingerprints, counts and image bytes; fresh capture IDs/timestamps/checksum chains legitimately differ, so whole-file digests identify captures rather than prove their logical equality. Task/snapshot/comment summary APIs are bounded; use the full capture and reviewed destination-row checks for completeness. Resolve any mismatch before writes or traffic switch.
6. Establish the approved private local backup destination, credential-renewal method and failure reporting. Install a schedule only when its owner, path, cadence and operational action are authorized; a production deployment or timer example alone does not install or verify one. Within the owner's authorized cutover scope, record the verified result and boundary before routing traffic or enabling destination writes. Only one board may accept writes. Keep the original board read-only and the source capture untouched for the agreed rollback period.

Keep private evidence of source/destination counts, record and image comparisons, upload retry results, application/configuration revisions, authorization scope and unresolved limitations. Evidence must not expose task text or credentials in operational logs. An offline single-writer before/after rehearsal proves recovery of its complete captures; it does not prove merging two writable production databases.

## Rollback without losing post-cutover work

If no destination writes were accepted, restore the previous routing/configuration only after confirming that boundary; verify the untouched source and access checks, then reopen source writes with approval. Preserve the failed destination and evidence for diagnosis.

If destination writes were accepted, make both boards read-only and drain in-flight mutations/uploads before rollback. Capture a complete verified destination v3 migration backup with authoritative attachment retry state and retain the original pre-cutover snapshot/package. Identify post-cutover events by the recorded boundary, stable record IDs and task/comment request keys; timestamps alone are insufficient, and regenerated database rowids/comment sequence numbers are not cross-system boundaries. Compare task and comment revision chains, newly created records, archive/restore state, snapshots, attachment retry metadata and all new/retained image bytes. Resolve conflicting changes explicitly with the owner. Do not replace the source with an old snapshot or perform a portable copy import, since either can lose updates or change IDs.

Reconcile the verified post-cutover changes into an isolated exact recovery plus retry metadata, or a reviewed owner-scoped migration, preserving event order, task/comment request-key idempotency, upload retry continuity, revisions and image relationships. A complete after-boundary capture can retain a sole writer's prior and new history; the offline tool does not merge two live databases; v3 recovery preserves original upload retries only under the unchanged storage owner, while v2 cannot restore those fields. A conflicting merge needs its own reviewed procedure. Rehearse and read back the reconciled result before reopening source writes or switching traffic back. If reconciliation or retry continuity cannot be proved safe, keep both boards read-only and preserve both captures until the owner decides how to resolve the conflict. Never silently discard destination writes to make rollback appear complete.
